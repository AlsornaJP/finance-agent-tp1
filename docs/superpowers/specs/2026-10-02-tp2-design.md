## Objetivo

Evoluir o agente do TP1 (um CSV entra no prompt, uma análise sai) para um protótipo funcional que:

1. age sobre dados externos por meio de tools (`@function_tool`);
2. resolve uma tarefa complexa em etapas (prompt chaining least-to-most + chain-of-thought);
3. lembra de interações anteriores em duas camadas: sessão (`SQLiteSession`) e RAG com embeddings;
4. combina tools e `output_type` Pydantic no mesmo agente;
5. é avaliado com métricas explícitas (A/B e ciclo Prompt-Response-Reflect-Revise);
6. documenta os seis entregáveis da Etapa 1.5 dos slides (arquitetura-alvo com 9 componentes).

Princípio transversal herdado do TP1: simplicidade e código limpo, nomes claros, poucos comentários.

### Lição do TP1 que orienta o desenho

Na Parte 5 do TP1 o LLM perdia transações e errava somas quando acumulava muitas tarefas num único
prompt. Regra do TP2: **o LLM nunca faz conta**. Leitura do CSV, somas, percentuais, variações e
critério numérico de anomalia são código determinístico exposto como tools; o LLM classifica,
interpreta e redige.


## Modelo de dados (entregável 6)

**`transacoes`**

| Campo | Tipo | Descrição |
| --- | --- | --- |
| `id` | INTEGER PK | Identificador |
| `data` | TEXT | Data ISO `AAAA-MM-DD` |
| `descricao` | TEXT | Descrição original do extrato |
| `valor` | REAL | Valor absoluto, sempre positivo |
| `tipo` | TEXT | `entrada` ou `saida` |
| `categoria` | TEXT NULL | Uma das 9 categorias fixas; nula até a classificação |
| `justificativa` | TEXT NULL | Raciocínio do classificador (CoT) |
| `arquivo_origem` | TEXT | CSV de onde veio |
| `ocorrencia` | INTEGER | Ordem da repetição de uma linha idêntica dentro do mesmo CSV (1, 2, ...) |

Restrição `UNIQUE(data, descricao, valor, tipo, ocorrencia)`: reimportar um extrato não duplica
linhas, e duas compras idênticas legítimas no mesmo dia não são descartadas.

**`trechos_guia`**: `id`, `secao`, `texto`, `embedding` (JSON). Regenerada quando o hash do guia muda.

**`memorias`**: `id`, `sessao`, `criado_em`, `texto` (pergunta + resposta), `embedding` (JSON).

**`metadados`**: `chave`, `valor` — guarda o hash do guia indexado.

O `SQLiteSession` usa suas próprias tabelas no mesmo arquivo.

## Tools

| Tool | Retorno |
| --- | --- |
| `gasto_total_mes(mes)` | total gasto, nº de transações, renda do mês, % da renda gasta |
| `gastos_por_categoria(mes)` | por categoria: valor, quantidade, % do total, % da renda |
| `comparar_meses(mes_atual, mes_anterior)` | por categoria: os dois valores, diferença em R$, variação em % |
| `transacoes_atipicas(mes)` | transações com valor > 10× a média das demais da mesma categoria (todo o histórico, mínimo de 2 para comparar), com a razão |
| `listar_transacoes(mes, categoria=None)` | as transações do filtro |
| `buscar_conhecimento(consulta)` | 4 trechos mais similares entre guia e memórias, cada um com sua origem |

Valores arredondados a 2 casas no código. Mês sem dados retorna estrutura vazia com aviso
explícito, nunca erro silencioso.

## RAG

- Embeddings: `gemini-embedding-001` via Google AI Studio, endpoint compatível com OpenAI, usando
  `GOOGLE_API_KEY` e o cliente `AsyncOpenAI` já existente. Sem dependência nova.
- Guia dividido por seção `##`; embeddings gerados uma vez e cacheados no SQLite.
- Cada `perguntar` grava pergunta + resposta em `memorias` com embedding.
- Busca: similaridade de cosseno em Python puro sobre guia + memórias, top 4.
- Conteúdo do guia (escrito por Claude, revisado pelo aluno): regra 50/30/20, faixas recomendadas
  por categoria, reserva de emergência, sinais de alerta, assinaturas.

## Agentes e fluxos

### `importar` — classificador com chain-of-thought

1. Python lê o CSV (`csv`), normaliza valores para positivos e insere em `transacoes`.
2. Seleciona as saídas sem categoria e envia ao classificador em JSON (`id`, `descricao`, `valor`).
3. `output_type = ClassificacaoLote`: lista de `{id, justificativa, categoria}`. A justificativa
   precede a categoria no schema (CoT). `categoria` é `Literal` das 9 categorias fixas.
4. Ids faltantes: uma nova chamada só com eles; persistindo a falta, `Não identificado`.

### `perguntar` — assistente com tools, sessão e RAG

- Tools: as seis acima. Sessão: `SQLiteSession(sessao, "data/financas.db")`.
- `output_type = RespostaFinanceira`: `resposta` (texto), `valores_citados` (lista de
  `{descricao, valor, ferramenta}`), `fontes_conhecimento` (lista de strings).
- Após o run, grava a interação em `memorias`.
- Demonstração de memória:
  - mesma sessão em runs distintos: "Quanto gastei com Alimentação em abril?" → "E em março?";
  - sessão nova: na `joao-1` o usuário declara "minha meta é gastar no máximo R$ 600 com Lazer";
    na `joao-2` pergunta "estou dentro da minha meta?" e o agente recupera a meta via RAG.

### `diagnosticar` — prompt chaining least-to-most

| Etapa | Executor | Saída |
| --- | --- | --- |
| 1. Levantamento | Python, chamando as funções de cálculo | `LevantamentoMensal` |
| 2. Pontos de atenção | LLM | `PontosDeAtencao` — categorias/transações que merecem análise e por quê |
| 3. Confronto com o guia | RAG por ponto + LLM | `AvaliacaoGuia` — dentro/fora do recomendado, com trecho citado |
| 4. Recomendações | LLM | `DiagnosticoMensal` — resumo, avaliações, recomendações priorizadas |

Cada etapa recebe em JSON as saídas das anteriores. O log registra entrada e saída de cada etapa.

### Natureza do sistema

Agentes especializados orquestrados por código, não multiagente no sentido do SDK (sem handoffs
nem agents-as-tools). O multiagente aparece na arquitetura-alvo documentada (entregáveis 3–5),
implementada nos TPs seguintes.

## Modelos e fallback

- Mantém a cadeia: OpenRouter (modelo principal → fallback) → Google AI Studio.
- Verificação inicial obrigatória: Gemma `:free` com tool calling + `output_type` no mesmo agente,
  e `SQLiteSession` com a API `chat_completions`.
- Se o Gemma falhar com tools, acrescentar modelos Gemini do AI Studio (ex. `gemini-2.5-flash`)
  ao `.env` e à cadeia de fallback.

Toda execução gera `.md` em `prompts/outputs/` com: instructions, input, chamadas de tool

## Avaliação (`evaluation/`)

### A/B — sem tools vs com tools

- Gabarito: `evaluation/gabarito_categorias.csv` (categoria correta de cada transação dos dois
  CSVs, preenchido por Claude e revisado pelo aluno); totais por categoria/mês calculados em Python.
- Variante A: prompt da Parte 5 do TP1, CSV no prompt, sem tools.
- Variante B: pipeline do TP2 (classificador + totais via tools).
- Métricas: precisão numérica (fração de valores categoria×mês iguais ao gabarito, tolerância
  R$ 0,01, mais erro absoluto do total) e acurácia de classificação.
- 3 execuções por variante por CSV; cada variante usa banco temporário próprio.
- Resultado e decisão justificada em `evaluation/resultado_ab.md`.

### Prompt-Response-Reflect-Revise

- Alvo: instructions do agente `perguntar`.
- Conjunto fixo de ~5 perguntas com respostas numéricas conhecidas.
- Métrica: rastreabilidade (fração de `valores_citados` que coincidem com o retorno de alguma
  tool da execução) e acerto da resposta.
- Até 3 versões; reflexões e versões do prompt registradas em `evaluation/prrr.md`.
